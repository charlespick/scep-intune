# Kubernetes: secretless deployment with workload identity federation

With `intune.auth: workload_identity`, the bridge holds **no Entra secret**.
Kubernetes projects a short-lived, audience-bound service account token into
the pod; the bridge presents it to Entra ID as a client assertion, and Entra
exchanges it for an app token because the app registration has a **federated
identity credential** trusting your cluster's service account issuer for this
one service account. The kubelet rotates the token; the Azure SDK re-reads the
file at least every 10 minutes. There is nothing to rotate, expire or leak.

The two **webhook secrets remain**: they are generated by step-ca and shared
with it, so no identity federation can replace them. Mount them from a
Kubernetes Secret (or the Secrets Store CSI driver) as files, and pass the
paths with `SCEP_VALIDATE_SECRET_FILE` / `SCEP_NOTIFY_SECRET_FILE`, rather than
as environment variables, which are visible to anything that can read the
pod spec or the process environment.

## 1. Entra: federated credential on the app registration

Use the app registration from [step-ca-setup.md](step-ca-setup.md#1-entra-id-app-registration)
(with the `scep_challenge_provider` and `Application.Read.All` application
permissions, admin-consented), **without** a client secret. Add a federated
credential for the bridge's service account:

```json
{
  "name": "scep-intune-k8s",
  "issuer": "<your cluster's service account issuer URL>",
  "subject": "system:serviceaccount:scep-intune:scep-intune",
  "audiences": ["api://AzureADTokenExchange"],
  "description": "scep-intune bridge pods"
}
```

```bash
az ad app federated-credential create --id <app-object-id> --parameters credential.json
```

- **issuer**: on AKS, `az aks show -g <rg> -n <cluster> --query oidcIssuerProfile.issuerUrl -o tsv`
  (the cluster needs `--enable-oidc-issuer --enable-workload-identity`). On
  another cluster, its `--service-account-issuer`, whose discovery document and
  JWKS must be reachable by Entra ID.
- **subject**: `system:serviceaccount:<namespace>:<service account>`, exactly.
  Only pods running as that service account can obtain the token, so treat
  the right to create pods with it in that namespace as equivalent to holding
  the Intune credential: keep the namespace dedicated and its RBAC tight.
- **audience**: `api://AzureADTokenExchange` in the commercial cloud;
  `api://AzureADTokenExchangeUSGov` or `api://AzureADTokenExchangeChina` in
  those clouds. The projected token's audience must match.

Remove any client secrets from the app registration once the federated
credential works, so no secret credential exists at all.

## 2a. AKS (or any cluster running the Azure workload identity webhook)

The webhook mutates pods labelled `azure.workload.identity/use: "true"`: it
projects the token and injects `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`,
`AZURE_FEDERATED_TOKEN_FILE` and `AZURE_AUTHORITY_HOST`. The bridge uses the
first three when its own settings are empty; don't hard-code the token path.

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: scep-intune
  namespace: scep-intune
  annotations:
    azure.workload.identity/client-id: "<app (client) ID>"
    azure.workload.identity/tenant-id: "<tenant ID>"
automountServiceAccountToken: false   # the bridge never calls the Kubernetes API
```

and in the pod template:

```yaml
metadata:
  labels:
    azure.workload.identity/use: "true"
spec:
  serviceAccountName: scep-intune
  containers:
    - name: scep-intune
      env:
        - name: INTUNE_AUTH
          value: workload_identity
```

## 2b. Any other cluster (no webhook)

Project the token yourself and point the bridge at it:

```yaml
spec:
  serviceAccountName: scep-intune
  containers:
    - name: scep-intune
      env:
        - {name: INTUNE_AUTH, value: workload_identity}
        - {name: INTUNE_TENANT_ID, value: "<tenant ID>"}
        - {name: INTUNE_CLIENT_ID, value: "<app (client) ID>"}
        - {name: INTUNE_FEDERATED_TOKEN_FILE, value: /var/run/secrets/entra/token}
      volumeMounts:
        - {name: entra-token, mountPath: /var/run/secrets/entra, readOnly: true}
  volumes:
    - name: entra-token
      projected:
        sources:
          - serviceAccountToken:
              path: token
              audience: api://AzureADTokenExchange
              expirationSeconds: 3600
```

## 3. A hardened Deployment

Released images are at `ghcr.io/charlespick/scep-intune` (see
[Releasing](../README.md#releasing)); each GitHub release names its image
digest. Reference the image **by digest**. A deployment that suits software
in a CA's issuing path:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: scep-intune
  namespace: scep-intune
spec:
  replicas: 2
  selector: {matchLabels: {app: scep-intune}}
  template:
    metadata:
      labels:
        app: scep-intune
        azure.workload.identity/use: "true"
    spec:
      serviceAccountName: scep-intune
      automountServiceAccountToken: false
      securityContext:
        runAsNonRoot: true
        runAsUser: 65532
        runAsGroup: 65532
        fsGroup: 65532
        seccompProfile: {type: RuntimeDefault}
      containers:
        - name: scep-intune
          image: ghcr.io/charlespick/scep-intune:<version>@sha256:<digest>
          args: ["-config", "/etc/scep-intune/config.yaml"]
          env:
            - {name: INTUNE_AUTH, value: workload_identity}
            - {name: SCEP_VALIDATE_SECRET_FILE, value: /var/run/secrets/scep/validate}
            - {name: SCEP_NOTIFY_SECRET_FILE, value: /var/run/secrets/scep/notify}
          ports: [{name: https, containerPort: 8443}]
          readinessProbe: {httpGet: {path: /healthz, port: https, scheme: HTTPS}}
          livenessProbe: {httpGet: {path: /healthz, port: https, scheme: HTTPS}}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: {drop: ["ALL"]}
          resources:
            requests: {cpu: 50m, memory: 32Mi}
            limits: {memory: 128Mi}
          volumeMounts:
            - {name: config, mountPath: /etc/scep-intune, readOnly: true}
            - {name: webhook-secrets, mountPath: /var/run/secrets/scep, readOnly: true}
            - {name: tls, mountPath: /etc/scep-intune/tls, readOnly: true}
      volumes:
        - name: config
          configMap: {name: scep-intune}
        - name: webhook-secrets
          secret:
            secretName: scep-intune-webhook   # keys: validate, notify (base64 text as printed by step)
            defaultMode: 0400
        - name: tls
          secret: {secretName: scep-intune-tls, defaultMode: 0400}  # e.g. issued and renewed by cert-manager
```

with a config map such as:

```yaml
server:
  listen: ":8443"
  tls:
    enabled: true
    cert: /etc/scep-intune/tls/tls.crt
    key: /etc/scep-intune/tls/tls.key
    client_ca: /etc/scep-intune/tls/step-ca-root.crt   # mutual TLS: only step-ca may call
    client_dns_names: [ca.example.internal]            # one of step-ca's dnsNames
intune:
  auth: workload_identity
```

`/healthz` answers without a client certificate, so the kubelet's HTTPS
probes work with mutual TLS on. The bridge re-reads its certificate when the
mounted Secret is updated (Kubernetes updates Secret volumes in place, except
`subPath` mounts, so don't use `subPath` for the certificate).

And restrict the network to exactly what the bridge needs:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: scep-intune
  namespace: scep-intune
spec:
  podSelector: {matchLabels: {app: scep-intune}}
  policyTypes: [Ingress, Egress]
  ingress:
    - from:   # step-ca only
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: step-ca}}
          podSelector: {matchLabels: {app: step-ca}}
      ports: [{port: 8443, protocol: TCP}]
  egress:
    - ports: [{port: 53, protocol: UDP}, {port: 53, protocol: TCP}]   # DNS
    - ports: [{port: 443, protocol: TCP}]   # Entra, Graph, Intune (Microsoft-owned, many IPs)
```

The kubelet's probes come from the node and are not subject to the ingress
rule on most network plugins; if yours enforces it, also allow the node CIDR
on 8443. If your CNI supports FQDN egress rules (Cilium, Calico Enterprise,
an egress gateway), narrow the 443 rule to `login.microsoftonline.com`,
`graph.microsoft.com` and `*.manage.microsoft.com`.
